## How each gate runs

**Bytes, forbidden modules and dependencies** run in every production build (`npm run build`, step 5), so they fail closed in CI's `build` job on every PR. A budget problem exits 1 and leaves no `dist/`. A development build isn't checked: budgets hold for what ships. The analyzer writes what it read to `dist-report/chunk-graph.json`: per entry, the start, lazy and workers files with their bytes, modules and packages. The build fails on:

| Code | When |
| --- | --- |
| `budget/bytes` | an entry's start JS, CSS, HTML or fonts is over its row, raw or gzip |
| `budget/forbidden` | a module or file a gated category names is on an entry's start path |
| `budget/worker-only` | a module only the service worker runs (`WORKER_ONLY_MODULES` in `scripts/build/budgets.js`) is on a page's start. The list is the code #35 slice 3c moved off the pages' start, where a run-time filter had kept it in the bundle |
| `budget/lazy-only` | a module that loads only at its first use (`LAZY_ONLY_MODULES` in `scripts/build/budgets.js`) is on a page's start. The list is the block menus' roles and keys, which #14 slice 4 loads at a menu's first open |
| `budget/dependency` | an entry's graph holds a package its row doesn't allow, its row allows one the graph no longer holds, or its start holds one its row allows only in its lazy chunks and workers (`lazyDependencies`, as Popup's `valibot` is, in its send chunk alone) |
| `budget/layout` | the pages pass's two named chunks (`scripts/build/page-chunks.js`, #35 slice 4b-2) are out of place: a page of that pass loads Vite's preload helper from another chunk than `host`, a page of that pass loads the `adapter` chunk (the new tab, Popup and Side Panel read through #17's reader, #35 slices 4b-2, 4c and 4d), or recovery.html's start loads a chunk named `host` or `adapter`, which only the pages pass writes |
| `budget/entry` | a page or the service worker the build has with no row, a row for an entry it doesn't have that isn't `planned`, a `planned` row for one it has, a `startChunks` or `lazyChunks` name the build has no loader chunk for or the page's start doesn't `import()`, or a chunk the page's start `import()`s that its row names in neither |
| `budget/file` | `build/budgets.json` is missing, doesn't parse, or doesn't read as a budget file: an entry or forbidden category of the wrong shape, a `start` row that isn't `html`, `js`, `css` or `fonts`, or a limit that isn't whole bytes |

`npm run verify:fixtures` breaks each rule on purpose and checks that the build fails with its code (`test/build-fixtures/budget-*`). `budget-start-chunk` sets the new tab's JS row to 20 KiB, over the root and under the tab, and the build fails: the workspace chunk is counted. `budget-start-missing` points `startChunks` at a chunk that isn't built, and `budget-start-empty` empties it. `budget-library-classic` puts Fuse.js back on the new tab's start as a classic script, and `budget-background-dependency` bundles an unlisted package into the service worker. `budget-worker-only` puts the records' catch-up back on the new tab's start. `budget-lazy-only` imports the block menus' keys statically in place of the loader's load, which puts them on the new tab's start. `budget-layout-helper` leaves Vite's preload helper out of the `host` group, `budget-layout-recovery` gives recovery.html's pass both groups, `budget-layout-newtab` puts the new tab's root back on #17's full adapter, `budget-layout-popup` does the same for Popup's root, and `budget-dependency-popup` imports the quick note's schema on Popup's start. `budget-layout-sidepanel` and `budget-dependency-sidepanel` do the same for Side Panel's root, with the apply's schema. A static import beside the loader's `import()` doesn't get that far: the bundler warns that the `import()` can't make a chunk, and the build fails with `build/bundler-warning`.

**Timing and heap** run in CI's `perf` workflow (`.github/workflows/perf.yml`), on every PR push and every push to `next`. It's its own workflow, not part of `pr-gate`, so it never blocks a merge.

- It builds the candidate.
- It builds 1.4.0 from the `v1.4.0` tag with v1.4.0's own lockfile and build (`npm run perf:reference`) and checks it against the digest pinned in `build/budgets.json`. A mismatch fails the job: a run against any other package would compare against the wrong one.
- It runs `npm run perf:probe` with 1.4.0, 1.4.0 again and the candidate: 12 rounds each on `typical` and `maximal`, with `--baseline build/budgets.json`.
- `scripts/perf/gate-report.js` writes the job summary, even when the probe exits 1 for an invalid run. For each profile it shows whether the run is valid, the candidate's median ratio to both 1.4.0 runs against the 7% row, its heap against 3.28 MiB plus 3%, and the absolute milliseconds beside them. A profile is invalid when 1.4.0 against itself is more than 7% off, when any round of any package failed, when the probe reported a problem (a fixture that isn't the recorded one, for one), or when fewer rounds have a run of every package than the probe asked for, or than the 12 the timing row takes. A package that measured nothing, say because every candidate round failed, makes it invalid too, rather than stopping the summary. So does a profile either row takes that the run has no rounds of, so a run that measured nothing can't pass. Then its timing and heap both say `invalid`, with the reasons listed. Each row fails the job only on the profiles it takes, and a gate row that names no profile fails it. The probe lists its problems for the whole run, not by profile, so one about a profile a row doesn't take still makes that row's profiles invalid.

Both rows say `mode: gate`. A timing fail, a heap fail, or a run the summary calls invalid fails the `perf` job.

## Changing a number

1. Measure it: `npm run build` prints each entry's start, and `dist-report/chunk-graph.json` has the rest. For timing, use `npm run perf:probe` interleaved against 1.4.0.
2. Take the number and its evidence to the owner through the lead.
3. Change the row in a PR that says why and links the evidence, and get it reviewed. Nothing else writes the file.
